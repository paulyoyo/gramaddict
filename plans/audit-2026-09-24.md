## 1. Summary

- **One critical issue, live on the Pi:** block detection has been OFF since 2026-09-23. The
  `--disable-block-detection` flag is `store_false`, so `disable-block-detection: false`
  gives `True`. Commit `c4ff2cf` ("fix inverted check") inverted a check that was correct.
  Verified by parsing with the Pi's ConfigArgParse 1.5.3. The Pi log's last
  "Checking for block…" line is from 2026-09-22 23:23.
- **Reply flow (integrations):**
  - A DeepSeek error, or a reply DeepSeek is unsure about, removes the person from the queue
    even when the Slack alert fails.
  - "NOT SURE" or "NONE" from DeepSeek is parsed as NO.
  - The Telegram token and Slack webhook can leak into logs, and the Telegram request and adb
    calls have no timeouts.
- **Unfollow (plugins):**
  - `unfollow-any-followers` also unfollows non-followers.
  - The search-based `unfollow` (Paul's job) records a person as UNFOLLOWED whenever a UI step
    fails, so they are never retried.
  - `do_unfollow` clicks a button it just failed to find.
- **Tests:**
  - The suite has been red since before this fork's changes: a Windows-only path, pytest-mock
    not installed, and an assertion that never passed.
  - CI never runs pytest, and there's no pytest config.
  - Some tests exercise copies of production code, and some leak global state (`requests.post`).
- **Packaging:** `gender-guesser` is missing from pyproject, the 4 dependency lists disagree,
  and `extra/configs-loader` never passes `--config`.

## 2. Decisions for Paul

1. **Unsure replies.** Today an unsure reply, or any DeepSeek error, sends a Slack alert and
   drops the person. Should they stay in the queue until you answer by hand? Recommended:
   drop them only after the Slack alert has actually been delivered, and retry DeepSeek
   errors first.
2. **Logs with DM text** (B6). The log file keeps every reply's full text and username.
   Keep it for debugging, or log only the first ~20 characters?
3. **Duplicated plugin loop** (P1/SOLID, size L). Should the 13 copies of the per-source
   `run()` loop become one shared job runner? The copies have already drifted into bugs
   (`interact-from-file` isn't wrapped in `run_safely`).
4. **`deploy.yml`** publishes this fork to PyPI under upstream's `GramAddict` name
   (`flit publish`). Delete the workflow?
5. **`gramaddict init`** downloads upstream's example files, not this fork's. Point it at
   `paulyoyo/gramaddict`, or leave it?
6. **B1** (entrypoints #6, promotional DM templates): already decided on 2026-09-22.
   Listed here only so it isn't lost; no action.
